Dès le début (fort impact, peu de complexité)
Catégories de tickets — Sans ça, tout est dans le même sac : routage, stats et formulaires par type de demande deviennent confus. C’est le premier levier d’organisation.

Priorités — Aligner l’équipe sur ce qui est urgent ou non ; indispensable pour le tri et, plus tard, pour les SLA.

Fonctions métiers — Utiles pour savoir qui couvre quel périmètre (RH, IT, etc.), distinct des rôles système (permissions).

Règles de base des tickets — Au minimum : catégorie / priorité par défaut, et si les membres peuvent modifier (ou supprimer) leurs tickets. C’est ce qui évite les mauvaises surprises dès les premiers tickets (déjà présent côté paramètres « Configuration des tickets » dans vos traductions).

Équipe et rôles — Inviter les gens et avoir admin / agent / membre (et permissions) clairs : sans ça, le support n’est pas exploitable en groupe. (Souvent une étape onboarding séparée chez vous, mais elle fait partie du même « démarrage support ».)

Très utile juste après (dès que le flux tourne)
Groupes d’équipe / files (vous avez un onglet groups dans Settings) — Pour répartir les tickets par équipe une fois le volume ou la structure grost.

Au moins un formulaire de demande — Votre onboarding le met en étape dédiée : c’est cohérent, car ça structure les données entrantes sans tout mettre en commentaire libre.

Canal email entrant (si vous recevez du support par mail) — À activer quand le besoin réel existe ; ce n’est pas toujours le jour 1, mais c’est souvent le prochain gros levier après le portail web.
